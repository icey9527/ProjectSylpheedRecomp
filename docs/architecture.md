# 代码结构与修改位置

## 当前实际目录

```text
repo/
  src/app/                手写宿主入口及 ReXApp 配置
  config/                 函数发现等分析修复
  scripts/                生成、检查、符号查询工具
  docs/                   结构、构建、维护及路线图
  generated/              自动生成的 PPC 转译代码（忽略，不手改）
  out/                    CMake 构建结果（忽略）
  CMakeLists.txt
  CMakePresets.json
  project_sylpheed_manifest.toml
```

外层 `assets/`、`symbols/`、`plans/`、`logs/`、`tools/` 以及 AI 手册和交接文件均只保存在本机。
手写宿主入口已移到 `src/app/`，CMake 已同步源文件路径。

## 怎样按模块组织

按符号查询分类是有用的，但不能按名字直接拆散生成 C++。
生成器按大小分文件，重新生成会重新安排代码；移动或改名会破坏自动化和注册关系。
函数也可能因链接器合并而拥有多个名字，原来的源文件结构无法仅靠函数名完整恢复。

维护采用两层：生成代码保持原样；手写补丁、配置和宿主适配按职责建目录。
只有出现真实代码时才新增目录，建议如下：

| 内容 | 后续位置 | 判断依据 |
| --- | --- | --- |
| 启动、窗口、路径、运行时配置 | `src/app/` | ReXApp 生命周期与宿主入口 |
| 特定游戏行为修正 | `src/patches/<模块>/` | 地址、符号、调用关系和实际缺陷 |
| 经验证需要的宿主系统适配 | `src/platform/windows/` | Windows API 与平台边界 |
| 一般函数边界/跳转配置 | `config/` | 分析诊断与镜像证据 |
| SDK 指令/运行时实现修复 | 单独维护的 SDK 源码或可重复补丁 | SDK 层问题；不能藏在 generated |

MAP 的 `2DGrpLib` 可作为 UI 调查线索，`xaudio/xact` 可作为音频线索，`xgraphics/d3d9` 可作为图形线索。
这些是“检索分组”，不等于已证实的修改范围；实际补丁目录要在检查调用关系后决定。
新增源码时同时更新 CMake 源文件列表；通过 SDK 官方注册/替换接口接入，不能仅增加一个未调用的函数。

## Xbox 依赖如何运行在 Windows

生成代码仍表达 Xbox 的寄存器、内存及调用语义，ReXGlue 运行时负责提供相应的内核/API 与设备支持。
Windows 图形默认采用 SDK 的 D3D12 后端；输入、音频等依赖使用 SDK 选定的实现。
所以首先是“生成代码 + ReXGlue 运行时 + 完整开发 SDK”构建和运行，而不是逐个把 Xbox 库替换成 Windows 库。

只有基线运行暴露具体缺口、性能或功能需求时，才做局部宿主适配。
这类修改必须考虑数据布局、调用约定、线程/回调、端序及错误行为，不能因名字像 Windows 函数就直接替换。
目前尚未验证宿主构建，也未验证游戏运行，先不进行大范围平台重写。
