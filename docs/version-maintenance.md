# 开发版、零售版修复与功能维护

当前只推进开发版，已显示 GP_TEST 调试菜单，保留开发镜像与配套符号。
按用户最新选择，零售版无限期延后、可以不实施；下文跨版本维护方法仅为未来重新启用时的参考。
用户希望保留开发版调试能力；菜单可见，具体选项、热键、诊断模式仍需逐项运行验证。
Windows 宿主 Debug 编译配置不等于 Xbox 游戏内部调试模式。
试玩版退出日常生成、构建和运行管线，仅在难以定位问题且有具体对照价值时参考。

## 两版主程序怎么修

当前“源码”是 PPC 指令转译得到的 C++，不是恢复出的原始游戏工程。
两版函数地址、内存布局、编译器优化、调用及数据引用可能不同，因此不能直接合并生成文件或移植一个地址补丁。
维护按具体问题和功能迁移：

1. 在问题发生的版本复现并记录输入 SHA256、地址、名字线索、调用/数据关系和运行日志。
2. 判断是 SDK 通用语义、宿主功能，还是某版游戏特定行为。通用 SDK 修复保留可重复源码补丁，并分别验证受影响版本。
3. 若要另一版也应用，先核对对应函数和前后行为；找不到可靠对应关系就保留待验证，不把相同地址/相似名字当证据。
4. 实现放手写模块、分析配置或 SDK 补丁，生成代码可重建。每版分别验证构建和触发场景；保存开发版的对应验证结果。
5. 版本特定修复标明适用镜像。零售版已改进的某个行为，只有在差异清楚、可验证时才回移开发版；无需把整份零售程序塞进开发程序。

不会因零售版名称就假定它每个功能都更好，也不会因开发版有符号就认定它最终一定更适合运行。
当前不自动推进零售或迁移目标；需要重新启用时依据具体成本与用户选择制定新计划。

## 零售版没符号还能维护吗

可以。符号帮助定位和理解，但维护并不要求先恢复全部原始名字或源文件树。
用开发版的名字作为候选线索，再比较指令/控制流、调用者与被调用者、字符串、常量和数据结构。
优化、内联和链接合并可能造成一对多/多对一；对应关系需要保留置信度和未确定部分。
当前尚未建立零售函数映射，不能宣称开发 MAP/PDB 已应用到零售版。

关键函数对应记录至少包含：

| 字段 | 要记录的内容 |
| --- | --- |
| 功能/模块 | 为什么需要研究这段代码；启动、UI、音频、图形等 |
| 开发版位置 | 输入 hash、地址、原始/可读名字、别名、MAP/PDB 匹配状态 |
| 零售版位置 | 输入 hash、地址、目前知道的名字/地址名称；未知明确写未知 |
| 对应证据 | 指令/控制流、调用、数据或运行证据；不能只写地址偏移 |
| 对应类型 | 一对一、一对多、多对一或尚不确定 |
| 修改与验证 | 改动文件、适用版本、触发场景、结果和未解决问题 |

有真实对应关系后再增加映射记录，不创建一张假装全部匹配的表。

## 整洁代码与新增功能

生成层保留可再生成性；名字和模块分类放在查询索引、映射记录和手写层。
手写层按职责组织，共用逻辑与版本接入分开，见 [architecture.md](architecture.md)。
不为整理外观人工重排几百万行生成 C++，也不为分类先重写所有函数。

宿主级功能（例如调试显示、配置界面或输入选项）可在确认 SDK 接口后放独立模块。
要修改游戏行为的功能，则确定对应版本的接口、数据布局与生命周期，再通过正式替换/注册接口接入。
零售版缺少原有调试功能时，不保证可以自动拷贝；优先保留开发运行配置，后续按实际需求增加独立宿主调试工具。
地址绑定到对应版本，通用模块不散布未经认证的 guest 地址。新增真实代码时同步 CMake 和验证场景。

这是一条逐步修复与局部增加功能的维护路线，不要求恢复完整游戏源码。
